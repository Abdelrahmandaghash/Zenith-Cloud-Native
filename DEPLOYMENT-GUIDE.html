1 What you are building

Read this first — every later step is just plumbing for this picture.

ZENITH is a small e-commerce + expeditions website split into independent services (a microservices architecture). Instead of one big program, you have several small programs that talk over HTTP:

Browser ──HTTP──▶ Nginx Gateway (:80) ◀── "the front door" │ ┌───────────────┼────────────────┬─────────────────┐ ▼ ▼ ▼ ▼ React Frontend Product API Tour API Order API (:8080) (:8001) (:8002) (:8003) │ │ │ ▼ │ PostgreSQL (:5432) │ Prometheus (:9090) ──scrapes /metrics──▶ all 3 APIs Grafana (:3001) ──reads Prometheus──▶ dashboards
ComponentJobWhere it runs
FrontendReact UI (shop, expeditions, cart)Local / ECS Fargate
Product serviceLists equipment, categories, searchLocal / ECS Fargate
Tour serviceLists mountain expeditionsLocal / ECS Fargate
Order serviceAccepts checkout ordersLocal / ECS Fargate
Nginx gatewayReverse proxy — routes URLs to servicesLocal only (AWS uses ALB)
PostgreSQLDatabase (for order persistence)Local / Amazon RDS
Prometheus + GrafanaMetrics collection + dashboardsLocal only (by design)

Three ways to run this project:

🟢 Path A — Local (Docker Compose): fastest, free, best for development.

🔵 Path B — AWS (Terraform → ECS/RDS/ALB): what you show in interviews as a cloud deployment.

🟠 Path C — Jenkins: automates Path B — push code, pipeline deploys for you.

Before Terraform or the AWS CLI can do anything, AWS must know who you are. Credentials are stored on your machine only — never in the repo, never in chat.

Option 1 — interactive setup (recommended for beginners) 
PS> aws configure

AWS Secret Access Key [None]: ...................... # paste secret

Option 2 — verify it worked (this must print YOUR account) 
PS> aws sts get-caller-identity
{
    "Account": "123456789012",

⚠️ Security note: if AWS keys were ever shared (file, chat, screenshot) — rotate them: AWS Console → IAM → Users → your user → Security credentials → deactivate old key → create new one. Treat exposed keys as stolen.

4 Path A — Run locally with Docker Compose

Fastest way to see the app working. Free. No AWS needed.

What Compose does: docker-compose.yml is a recipe that describes all 8 containers (gateway, frontend, 3 APIs, Postgres, Prometheus, Grafana) and how they connect. One command builds and starts all of them on a private network.

1 Make sure Docker Desktop is running

Look for the whale icon in your system tray. If it's not there, start Docker Desktop and wait until it says "Docker Desktop is running".

PS> docker version
# If this prints version info for Client AND Server, Docker is ready.
# If it errors → start Docker Desktop and wait ~30 seconds.

2 Build and start everything

PS> docker compose up --build -d

Explain each part:

PartMeaning
docker composeReads docker-compose.yml and manages the whole stack
upCreate the network + start all containers
--buildRebuild images from your Dockerfiles first (needed after any code change)
-dDetached — runs in the background so your terminal stays free

First run downloads base images and builds — expect 2–5 minutes. Later runs are seconds.

3 Check container health

PS> docker compose ps

Every service should show Up and (after ~15s) healthy. Why "healthy"? Each container runs a periodic healthcheck (curl its /health endpoint); Docker marks it healthy only if that keeps succeeding.

PS> docker compose logs -f product-service   # watch one service's logs (Ctrl+C to stop watching)

5 Verify the local app

Open these in your browser once containers are healthy.

WhatURLWhat you should see
Main sitehttp://localhostZENITH homepage (hero, products, tours)
Shophttp://localhost/shop15 products, filters, search
Expeditionshttp://localhost/expeditions6 mountain tours
Gateway healthhttp://localhost/gateway-health{"status":"healthy",...}
Frontend directhttp://localhost:3000Same site, bypassing gateway
Product APIhttp://localhost:8001/api/productsJSON list of products

How requests flow (try it yourself): visit http://localhost/api/products — the gateway sees /api/products and proxies it to the product service. Now compare with http://localhost:8001/api/products — same JSON, but you bypassed the gateway. That's what a reverse proxy does.

Quick end-to-end test: place an order from the UI

Add items to the bag → Proceed to Checkout → fill name/email/address → Confirm & Place Order. You'll see an order code like ZEN-ORD-12345. Then check http://localhost:8003/api/orders — your order is at the top of the list.

Known limitation: the order service keeps orders in memory. Restarting the container (docker compose restart order-service) wipes them. Postgres is running and wired via DATABASE_URL, but the service doesn't write to it yet — that's a deliberate "next feature", not a broken setup.

6 Path B — Run on AWS (Terraform)

Deploys the same containers to real AWS: ECS Fargate + ALB + RDS.

The mental model: locally, docker compose up starts containers on your PC. On AWS, Terraform creates the equivalent infrastructure (servers you don't see, load balancer, database), then your images run on it. Terraform = "recipe for cloud resources".

Local (Compose)AWS (Terraform)
docker buildECR (container registry — "private Docker Hub for your account")
containers on your PCECS Fargate (AWS runs your containers serverlessly)
Nginx gateway :80ALB (Application Load Balancer — routes URLs to services)
Postgres containerRDS (managed database — backups/patching handled by AWS)
docker compose logsCloudWatch Logs

1 Initialize Terraform

Downloads the AWS provider plugin (one-time).

PS> cd terraform
PS> terraform init
Terraform has been successfully initialized!

Why: Terraform doesn't ship with AWS support built-in; init downloads the hashicorp/aws provider so Terraform knows how to create AWS resources.

2 Review what will be created

PS> terraform plan

Terraform prints a diff: + create for ~40 resources (VPC, subnets, security groups, 4 ECR repos, ECS cluster/services, ALB, RDS, IAM roles, log groups...). Read it — never apply what you don't understand.

Defaults are fine to start: region us-east-1, RDS db.t3.micro, everything named zenith-dev-*. Want to change something? Copy terraform.tfvars.example → terraform.tfvars and edit.

3 Create the infrastructure

PS> terraform apply
# type:  yes   (confirm)
Apply complete! Resources: ~40 added.

Takes ~5–10 minutes. At this point the "shell" exists — but ECS tasks will show errors like CannotPullContainerError because your images aren't in ECR yet. That's expected; Step 4 fixes it.

4 Grab the important addresses

PS> terraform output ecr_repository_urls
{
  "frontend" = "123456789012.dkr.ecr.us-east-1.amazonaws.com/zenith-dev-frontend"
  "product"  = "123456789012.dkr.ecr.us-east-1.amazonaws.com/zenith-dev-product"
  "tour"     = "123456789012.dkr.ecr.us-east-1.amazonaws.com/zenith-dev-tour"
  "order"    = "123456789012.dkr.ecr.us-east-1.amazonaws.com/zenith-dev-order"
}

ECR = Elastic Container Registry. It stores your Docker images in the cloud so ECS can pull them.

5 Log in to ECR

PS> $ACCOUNT = aws sts get-caller-identity --query Account --output text
PS> aws ecr get-login-password --region us-east-1 |
      docker login --username AWS --password-stdin "$ACCOUNT.dkr.ecr.us-east-1.amazonaws.com"

Why login? ECR is private. This exchanges your AWS credentials for a ~12-hour token that lets Docker push/pull images. (ECS itself uses an IAM role, not this token.)

6 Build & push all 4 images

PS> cd ..   # back to repo root
PS> $ACCOUNT = aws sts get-caller-identity --query Account --output text
PS> $ECR = "$ACCOUNT.dkr.ecr.us-east-1.amazonaws.com"

PS> docker build -t $ECR/zenith-dev-frontend:latest ./frontend
PS> docker push  $ECR/zenith-dev-frontend:latest

PS> docker build -t $ECR/zenith-dev-product:latest ./services/product-service
PS> docker push  $ECR/zenith-dev-product:latest

PS> docker build -t $ECR/zenith-dev-tour:latest ./services/tour-service
PS> docker push  $ECR/zenith-dev-tour:latest

PS> docker build -t $ECR/zenith-dev-order:latest ./services/order-service
PS> docker push  $ECR/zenith-dev-order:latest

build = compile image locally from the Dockerfile. push = upload it to ECR. ECS will pull :latest from here.

7 Tell ECS to start the tasks

PS> $CLUSTER = "zenith-dev-cluster"
PS> foreach ($svc in @("frontend","product","tour","order")) {
      aws ecs update-service --cluster $CLUSTER --service "zenith-dev-$svc" --force-new-deployment
    }
PS> aws ecs wait services-stable --cluster $CLUSTER `
      --services zenith-dev-frontend zenith-dev-product zenith-dev-tour zenith-dev-order

Explain: update-service restarts the service so it pulls the new images; ecs wait blocks until all tasks are running & healthy (takes 1–2 min).

8 Get your public URL

PS> terraform output app_url
"http://zenith-dev-alb-1234567890.us-east-1.elb.amazonaws.com"

Open it in a browser — same site as local. The ALB (load balancer) receives the request and routes by path: /api/products* → product service, /api/tours* → tour, /api/orders* → order, /* → frontend.

7 Verify the AWS deployment

7.1 All services running?

PS> aws ecs describe-services --cluster zenith-dev-cluster `
      --services zenith-dev-frontend zenith-dev-product zenith-dev-tour zenith-dev-order `
      --query "services[].{Name:serviceName,Status:status,Running:runningCount,Desired:desiredCount}"

Expected: every row shows Status: ACTIVE and Running == Desired.

7.2 Endpoints through the ALB

PS> $URL = (terraform output -raw app_url)
PS> curl "$URL/health"          # frontend OK
PS> curl "$URL/api/products"    # JSON from product service
PS> curl "$URL/api/tours"
PS> curl "$URL/api/orders"

7.3 Read the logs

PS> aws logs tail /ecs/zenith-dev-product --follow   # Ctrl+C to stop

⚠️ Cost alert: while running, AWS charges for the ALB (~$0.0225/hr), ECS Fargate vCPU/memory, RDS, and possibly data. When you're done experimenting → terraform destroy (Step 10). Idle-but-not-destroyed still costs money.

8 Path C — Jenkins CI/CD pipeline

Automates everything in Path B: push code → Jenkins builds, tests, deploys.

What Jenkins adds: without it, you run Steps 5–7 by hand every time you change code. With it, Jenkins runs the same commands automatically whenever you click Build or push to GitHub. That's CI/CD (Continuous Integration / Continuous Delivery).

8.1 The 6 stages in jenkins/Jenkinsfile

#StageRunsFails if…
1Checkoutgit clone your reporepo unreachable
2Static checkspy_compile ×3 + verify_all.pysyntax/config error
3AWS auth + ECR loginsts get-caller-identity, docker loginbad credentials
4Build & pushdocker build + push ×4build error / push denied
5Deployecs update-service --force-new-deployment + waittasks never stabilize
6Smoke testscurl /health, /api/products, /api/tours, /api/ordersany endpoint ≠ 2xx

1 Start Jenkins (local trial)

PS> docker run -d --name jenkins -p 8080:8080 -p 50000:50000 `
    -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts-jdk17
PS> docker logs jenkins 2>&1 | Select-String "Please use"
# Copy the initial admin password shown there.

Open http://localhost:8080 → paste password → Install suggested plugins → create admin user.

2 Add your AWS credential

Dashboard → Manage Jenkins → Credentials → System → Global credentials → Add Credentials:

FieldValue
KindUsername with password
IDaws-credentials (exact — the Jenkinsfile references this ID)
UsernameYour AWS Access Key ID
PasswordYour AWS Secret Access Key

Why this way? Secrets live in Jenkins' encrypted store, not in the Jenkinsfile or Git. The pipeline reads them at runtime via withCredentials.

3 Install agent tools

The machine running the job needs: Docker, AWS CLI, Python 3, Git. Quick check inside the Jenkins container (if you run Jenkins in Docker, it needs access to the host's Docker socket — for a serious setup use a separate Linux agent with these tools installed).

PS> docker exec jenkins sh -c "git --version; python3 --version; aws --version; docker version --format '{{.Server.Version}}'"

4 Create the job

New Item → Pipeline → name it (e.g. zenith-deploy) → under Pipeline section choose Pipeline script from SCM →

FieldValue
SCMGit
Repository URLhttps://github.com/Abdelrahmandaghash/Zenith-Cloud-Native.git
Credentials(none for public repo)
Branch*/master
Script Pathjenkins/Jenkinsfile

5 Run it

Click Build Now. Watch the Pipeline Steps view — each stage turns green as it passes. First run downloads the Jenkins image plugins etc. and builds 4 images, so allow ~10 minutes.

✅ Green = deployed. ❌ Red = click the failing stage → read the console output (the error is almost always there).

The loop you've built: change code → git push → (webhook or manual Build) → Jenkins tests → builds → pushes to ECR → updates ECS → curls the ALB. Zero manual AWS commands.

9 Monitoring (Prometheus + Grafana)

Local only — by design, to stay on the free tier.

How it works

each FastAPI service ──exposes──▶ /metrics (Prometheus text format) ▲ │ scrape every 5 seconds Prometheus (:9090) ──stores time-series data──▶ queries ▲ │ reads Grafana (:3001) ──renders──▶ dashboards (uptime, requests, latency, orders)
  1. Instrumentation — every service has HTTP middleware counting requests, status codes, latency (see track_metrics_middleware in each main.py).
  2. Scraping — monitoring/prometheus/prometheus.yml tells Prometheus to hit product-service:8001/metrics, tour-service:8002/metrics, order-service:8003/metrics every 5s.
  3. Visualization — Grafana auto-loads a datasource + dashboard from monitoring/grafana/provisioning/ (no clicking required).

View it

  1. Open http://localhost:9090 → Status → Targets → all 3 services should be UP.
  2. Open http://localhost:3001 → login admin/admin → dashboards folder "ZENITH Platform" → ZENITH — Microservices Health & Traffic.
  3. Click around the site to generate traffic, watch the charts move within 5–15 seconds.
MetricMeans
zenith_http_requests_totalHow many requests each service handled (by status code)
zenith_http_request_duration_secondsAverage response time
zenith_orders_created_totalTotal orders placed
zenith_service_uptime_secondsHow long each service has been running

10 Cleanup & stop everything

Stop local containers (keeps images & data)

PS> docker compose down

Removes containers + network. Volumes (Postgres/Grafana/Prometheus data) are kept. Restart later with docker compose up -d.

Full local reset (deletes DB data too)

PS> docker compose down -v        # -v removes named volumes

Destroy AWS infrastructure (stops all charges)

PS> cd terraform
PS> terraform destroy
# type: yes

This deletes everything Terraform created — ECS, ALB, RDS, ECR, VPC. RDS has skip_final_snapshot = true so no snapshot prompt. Re-running the AWS path later starts fresh.

Stop Jenkins

PS> docker stop jenkins

11 Troubleshooting

SymptomCauseFix
docker: command not found / daemon not running Docker Desktop not started Start Docker Desktop, wait for "running"
Port already in use (80/3000/8001...) Another process holds the port docker compose down first, or stop the conflicting app
Gateway 502 Bad Gateway Backend container starting/not healthy docker compose ps → wait or docker compose logs <service>
Frontend shows sample data only API unreachable → frontend falls back to local sample data (by design) Check docker compose ps; in dev mode check Vite proxy
CannotPullContainerError on AWS Images not pushed to ECR yet Run Step 6 (build/push) then Step 7 (force deployment)
An error occurred (AccessDenied) on push Not logged in to ECR / wrong account Re-run Step 5 (ECR login), verify aws sts get-caller-identity
terraform apply fails on RDS Account limits, service quotas, or name already exists Read the error; delete leftover via console; wait for RDS "processing" to finish
Jenkins stage 3 fails Credential missing or wrong ID Credential ID must be exactly aws-credentials
Jenkins stage 6 fails A service unhealthy after deploy Check ECS console → tasks → stopped reason; read CloudWatch logs
Grafana dashboard says "No data" Prometheus has no targets yet Open Prometheus → Status → Targets; generate traffic first
Orders disappear on restart Order service is in-memory (known limitation) Expected — add DB persistence to use RDS/Postgres
npm ci fails in frontend build No package-lock.json committed yet Run npm install locally once, commit the lockfile, then switch Dockerfile to npm ci

12 Glossary — what every term means

TermPlain-English meaning
ImageA frozen snapshot of your app + its dependencies (like an installer file)
ContainerA running instance of an image (like a program launched from an installer)
DockerfileThe recipe that builds an image (base OS → install deps → copy code → run)
Docker ComposeYAML that starts many containers together with one command — local orchestration
Reverse proxyA server that receives your request and forwards it to the right backend (Nginx/ALB)
Gateway / IngressThe single entry point that routes URLs to services
Load balancer (ALB)AWS's gateway: spreads traffic, health-checks, handles many servers
MicroserviceOne small service doing one job, deployed independently
HealthcheckA periodic test ("is this alive?") so Docker/AWS know when something is broken
ECRPrivate Docker image storage in your AWS account
ECS / FargateAWS's container runner; Fargate = no servers for you to manage
Task definitionThe blueprint for one container on ECS (image, CPU, RAM, env vars, ports)
Service (ECS)Keeps N tasks running, restarts failures, rolls out new versions
RDSManaged PostgreSQL — AWS handles backups, patching, uptime
VPC / SubnetYour private network in AWS; subnets are slices of it (public = internet-reachable)
Security GroupA firewall rule: which ports are open, and to whom
IAM RoleA permission set attached to services ("this task may pull from ECR")
Secrets Manager / SSMEncrypted storage for passwords — injected at runtime, never in Git
TerraformCode that creates/updates/destroys cloud resources — "infrastructure as code"
terraform planPreview of what Terraform would change (dry run)
terraform apply/destroyCreate the resources / delete them all
CI/CDAutomatically test (CI) and deploy (CD) every code change
JenkinsAn automation server that runs your pipeline (build → test → deploy)
PrometheusCollects numbers (metrics) from services over time
GrafanaDraws charts/dashboards from Prometheus data
Smoke testQuick "is it basically working?" checks right after deploying
Free tierAWS's free usage limits — but always destroy idle resources
